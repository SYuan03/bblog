01 · MOTIVATION代码存在，不代表行为成立

一份能打开的 index.html，可能处处断线

游戏把完整应用常见的集成故障压缩在一个页面里：输入、共享状态、渲染和状态机必须同时正确。

✓
HTML 可以加载语法、标签和入口文件都存在
✓
代码里有对应变量ammo、score、paused 看起来齐全
✓
画面能够渲染Canvas 或 WebGL 持续产出帧
≠
输入断了鼠标拖动没有触发上菜，玩家无法完成主循环。
状态断了暂停界面出现了，但单位和生产队列仍在推进。
组合断了场景加载和驾驶单测都过了，连在一起却冻结模拟时间。
恢复断了重新开始后，上一局的结果或临时对象仍然残留。

02 · THE ORACLE PROBLEM怎样到达状态，又不绑死实现

完整应用评测卡在两个极端之间

纯 GUI 难以稳定复现罕见状态；直接摸内部变量又会把测试写死在某一种实现上。

只靠用户操作

  • 到达后期状态耗时
  • 碰撞和时序容易漂移
  • 很难定位究竟哪条需求失败
论文选择的中间层

公开的行为契约

legal scenario
+ player action
+ stable snapshot
+ invariant

测试知道怎样准备合法状态、怎样操作、看哪些结果。游戏内部的数据结构仍由 Agent 自己决定。

直接注入内部状态

  • 依赖变量名和对象结构
  • 不同实现难以复用同一测试
  • 测试可能绕过真实玩法路径

05 · PUBLIC CONTRACT四个方法组成统一测试面

接口约束语义，不规定内部写法

window.__gameTest = {
  reset(options),
  loadScenario(name, options),
  input(action),
  getSnapshot()
}

// 每次调用都返回 JSON 可序列化快照
// 接口必须连接玩家实际看到的状态
reset恢复初始状态，清掉上一局的临时对象、弹窗和结果锁。
loadScenario建立普通游玩能够到达的前置状态，不能提前制造测试结果。
input执行玩家级动作，例如移动、射击、下单、暂停和重启。
getSnapshot输出稳定的语义摘要，不暴露私有对象图或源码名称。

06 · PREPARE, ACT, OBSERVE让罕见状态可达，同时保留因果链

测试可以把棋盘摆好，但不能替玩家落子

PREPARE

合法前置状态

例如运输车已经接近敌方基地，但 result 仍是 none。测试不必从开局等十分钟。

ACT

玩家级动作

等待、移动、开火或下达生产命令。行为必须对应玩家能做的事。

OBSERVE

结果与不变量

检查胜利、HUD、资源和结果锁是否同步；无关状态不能被偷偷改动。

契约明确禁止
直接设置胜负、资金、血量或坐标
暴露生成代码的私有对象和函数名
用固定值或 {ok:true} 伪造机制
维护一套不反映到画面的测试状态

08 · REAL TEST CODE持续开火：按下、观察、松开、再观察

测试追踪开火行为从增长到停止

// 摘自 p1-keyboard-sustained-fire-release
// 省略辅助函数和错误分支
const before = setup.snap;

await browser.keyDown('Space');
await browser.sleep(650);
const held = await game.snapshot();

await browser.keyUp('Space');
await browser.sleep(300);
const released = await game.snapshot();
const afterRelease = await game.wait(550);

const grewWhileHeld =
  count(held, 'projectiles') > count(before, 'projectiles') ||
  rev(held, 'projectiles') > rev(before, 'projectiles') ||
  num(held.helicopter?.ammo?.current) <
    num(before.helicopter?.ammo?.current);

const plateauAfterRelease =
  count(afterRelease, 'projectiles') <=
    count(released, 'projectiles') + 1 ||
  rev(afterRelease, 'projectiles') === rev(released, 'projectiles');

PASS = grewWhileHeld && plateauAfterRelease;
真实输入直接发送键盘按下与松开，不调用测试接口替代开火。
持续性按住期间，弹药、弹丸或战斗 revision 至少有一个变化。
释放语义松开后弹丸数量或 revision 停止继续增长。

16 · DIAGNOSTIC CASES通过很多检查，仍会在组合处失败

两个失败样本说明了 benchmark 在抓什么

Diner Dasher

GPT-6-Astra · Codex CLI
  1. 加载装有正确餐点的托盘场景。
  2. 从快照读取托盘和顾客的屏幕边界。
  3. 发送真实鼠标拖动与触摸序列。
  4. 两种输入都没有增加服务进度或收入。
L1、L2 P0 和 P2 都通过，P1 的真实输入检查仍判定核心交互失败。

Turbo Smash Beast

DeepSeek-V4-Flash · Claude Code
  1. 接口自测会显式推进模拟时间，因此通过。
  2. 单独的真实驾驶测试从全新页面开始，也通过。
  3. benchmark 先加载场景，再发送真实驾驶输入。
  4. 场景加载开启测试模式，意外关闭自然时间推进。
单个路径各自正常，组合路径冻结了车辆。加速、滑行及相关检查失败。

17 · READING NOTES这套方法适合回答什么，回答不了什么

它把“完整交付”变成了可定位的工程指标

方法做得扎实的地方

  • 测试契约在生成前固定，减少事后迁就某个实现。
  • 语义状态、真实输入和浏览器信号互相校验。
  • 严格成功与平均通过率同时报告，能看见局部完成和完整交付的差别。
  • 失败报告能落到具体需求和交互序列。

读结果时要带上的限制

  • 47 个单页游戏不能代表后端、数据库或多人系统。
  • 每个任务与配置只跑一次，没有方差或显著性分析。
  • 公开接口增加实现负担，也留下针对契约优化的空间。
  • P1 当前可返回 NOT_APPLICABLE；作者明确记录了这一点。
  • 评测主轴是功能合规；画面质量与游戏乐趣覆盖有限。
对 Coding Agent，接下来的难题已经很具体：同一份状态要同时经得住 API 读取、真实操作、画面反馈和重启后的再次验证。
