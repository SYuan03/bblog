02 · PART 0先说清楚谁执行、谁评分、训练什么

示范记录、执行环境与训练奖励，是三种不同的东西

MCP server

一组带名称、参数格式（JSON schema）和用途说明的工具。ASTRA 只在同一服务内组织可能连续调用的工具。

Trajectory · 完整记录

用户请求、模型推理、工具调用、工具返回和最终回答。生成这段记录的执行过程叫 rollout。

Environment · 环境

实际执行工具调用的程序。RL 阶段为每条问答生成固定 Python 模拟工具，不连接真实支付或医院系统。

Online RL · 在线训练

当前模型（policy）自己执行任务，按完成程度和调用次数获得奖励，再更新它的参数。工具本身不被训练。

本文的“多轮”主要指模型与工具的往返。训练尚不包含不断变化的用户对话；作者将其列为后续工作。

03 · 研究动机固定示范与当前模型的执行反馈各有作用

只有示范，学不到当前错误；只有奖励，初始模型又可能不会调用工具

训练材料难扩展

人工逐条写任务、工具实现和检查规则，很难覆盖大量领域和长调用链。

临时模拟不够稳定

由 LLM 每次临时编工具返回值，同一动作可能得到不同结果。执行过程与评分都难以固定。

RL 有起步困难

初始模型可能选不对工具、填错参数，很少完成任务。若同题尝试全失败，组内奖励没有好坏区别。

ASTRA 先用固定示范训练，再在每条样本独立的 Python 环境里让模型多轮执行；环境和目标固定，回答由当前模型重新生成。

来源：Introduction、Sections 3.1-3.2

06 · 示范构造1,585 个服务 · 19,036 份工具文档 · 41 个领域

先找可能连续调用的工具，再让模型真正执行任务

1 · 筛工具

服务至少有三个工具；说明足够具体，参数格式能转成 OpenAI 函数调用格式。

2 · 连关系

LLM 先提出任务和调用链；连续调用形成有向边，再沿图随机行走，限制链长。

3 · 验依赖

后续参数必须能从用户请求或前面返回值得到；任务也应与调用链一致。

4 · 造任务

按调用链或只按服务说明生成任务，再改写复杂度、表达方式和用户身份。

5 · 执行

Qwen-Agent 调真实服务或保存状态的模拟器；模拟调用有 20% 概率注入失败。

11 · 完整执行记录的奖励完成目标数与工具调用次数共同决定

解决更多子目标、少做冗余调用，奖励才高

n 是所需目标数，n̂ 是命中目标数，c 是工具调用次数。调用次数与对话轮数不要混用。

完成比例 r = n̂ / n　　调用效率 p = n̂ / (c + ε)　　F1 reward = 2pr / (p + r)

4 项全做对，调用 4 次

r = 1，p ≈ 1，F1 ≈ 1。每次调用都解决一个需要的目标。

4 项全做对，调用 6 次

r = 1，p ≈ 0.67，F1 ≈ 0.80。两次额外调用没有增加已解目标。

做对 3 项，调用 4 次

r = 0.75，p ≈ 0.75，F1 ≈ 0.75。只是公式示例，不是上一页样本的实测奖励。

忽略 ε 的极小修正。公开代码未包含完整 RL 训练/奖励实现；不能把公式代入当作真实模型日志或官方评分复现。

来源：Section 3.2.2、Equations 29-31；数值为条件代入

13 · 训练组怎样凑足奖励全相同的组没有相对好坏信号

只收集有组内奖励差异的记录，凑足训练 batch 再更新

同题多次尝试

当前模型为同一道题采样 G 条完整记录。

→
检查组内差异

Std(R) > δ 才有效。全同分时，GRPO 相对训练权重为零。

→
保留多余记录

缓冲区存未用的有效记录；不足目标数量就继续采样。

→
只更新 policy

每步凑足有效记录，训练调用工具的模型，不改工具和目标。

论文参数

batch 和 mini-batch 均为 256，学习率 2e-6；输入上限 25,600 tokens，回答上限 49,152 tokens，最多 32 轮。

目标函数

基于 GRPO；省去限制分布偏移的 KL 项与鼓励多样性的熵奖励。损失在整个 batch 的 token 上平均。

16 · 怎样解释增益先区分总增益，再看反例和消融

最终模型三榜都提升，但“RL 增量普遍最大”不够准确

基座到最终 RL

14B：BFCL 44.50→58.13，τ² 44.55→57.70，ACE 51.67→68.96。32B：47.88→64.25，49.70→63.70，59.79→71.88。

ACE 的 SFT 增量更大

14B ACE：SFT +16.04，随后 RL 仅 +1.25。RL 的大增量主要见于 BFCL 和 τ²，不能把 +17.29 全归 RL。

AIME 基本保留

14B 两种设置的平均近乎不变；32B 一种 -0.05，另一种 +1.00。只说明这两项数学评测未系统性退化。

SFT 也有退化项

BFCL Missing Function：14B 39.50→25.50，32B 52.50→40.00。最终 RL 恢复到 56.00 / 65.50；它检验缺少正确工具时能否拒绝调用。

奖励消融的具体证据

只奖完成比例，交互轮数激增后崩溃；只奖调用效率，模型过早停止、后期崩溃。F1 更稳定，但组件贡献没有完整组合控制。

18 · 保留什么，重新验证什么四层检查分别解释，不互相替代

训练分层值得借鉴，最终环境一致性仍需核查

论文已经给出

  • 从工具文档生成固定示范，从多步问答生成可执行环境。
  • F1 奖励兼顾完成目标与减少冗余调用。
  • 14B / 32B 的最终模型在三项工具使用评测均提升。
  • 公开数据生成代码、两个 1k 子集和模型。

证据尚有边界

  • 目标出现在输出中，只验证合成工具与答案自洽。
  • SFT 评分异常默认满分；污染规模没有统计。
  • 公开第 0 行支付工具重名、目标不匹配；请求无年份，预订实现却限定 2024 年。
  • 没有完整 RL 训练脚本、内部训练数据或多训练随机种子对照。
后续先在最终环境重放完整目标调用并检查工具名唯一；评分失败则重试或隔离。再用真实 API 或独立模拟器测试未见任务迁移。
