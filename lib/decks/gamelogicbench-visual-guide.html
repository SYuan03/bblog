02 · PART 0 / GODOTScene 是 Node tree

先把 Godot 想成一棵会运行的组件树

Level.tscn
├─ Player · CharacterBody2D
│　├─ Sprite2D
│　├─ CollisionShape2D
│　└─ Camera2D
├─ Enemy · CharacterBody2D
└─ HUD · Control
Node渲染、碰撞、相机、声音和输入等职责由不同节点承担。
Scene保存后的节点树可以像一种新节点那样被重复实例化。
Script脚本挂在节点上，通过回调和 signal 与整个 scene tree 协作。
Godot 4.4 官方文档：Nodes and Scenes。
03 · PART 0 / GDSCRIPT本文 Godot 4.4 示例，非 benchmark 代码

每个物理步读取输入；生命变化时发出事件

extends CharacterBody2D

signal health_changed(value: int)
@export var speed := 220.0
var health := 3

func _physics_process(_delta: float):
    var d := Input.get_vector(
        "left", "right", "up", "down")
    velocity = d * speed
    move_and_slide()

func take_damage(amount: int):
    health = max(health - amount, 0)
    health_changed.emit(health)
每个物理更新步读取输入、更新 velocity，再让引擎处理碰撞与移动。
Signal角色发出 health_changed，UI 可以订阅，而不用被写死在角色逻辑里。
为什么难测节点、回调与物理模拟会共同改变状态，不能只看最后数值。
Godot 4.4 背景示例，需 CharacterBody2D + 碰撞体，并在 Input Map 配 left/right/up/down 动作；不是论文任务。

05 · MOTIVATIONjudge 是检查运行状态与事件的判分程序

评测需要检查不同场景、全过程，并给出可重复的判定

固定示例不够

一条 preview 能通过，不代表换布局、输入顺序或数值后仍然正确。

最终状态不够

跨帧规则可能中途被破坏，最后又回到看似合法的状态。

录像不够

资源守恒、内部时序和状态继承问题未必直接出现在画面里。

模型 judge 不够稳定

交互选择和打分都含模型判断，重复运行可能给出不同 verdict，成本也高。

论文 §1。作者的目标不是评价美术与体验，而是确定性验证 gameplay logic。

11 · CRITERION VALIDATION先验证 judge，再拿 judge 评模型

既要放过不同的正确实现，也要抓住缺一项能力的错误实现

POSITIVE

正确实现

所有 scenario 与 seed 都通过，并远离容差边界。

MUST PASS
NEUTRALITY

等价正确实现

内部写法不同，但可观察行为相同。

MUST PASS
COMMON ERROR

常见错误实现

包含常见逻辑错误，用来证明测试不是只看能否运行。

MUST FAIL
TARGETED ERROR

单能力 mutant

刻意删掉一项能力的代码，至少一个目标场景要抓住它。

14 · TICK-LEVEL ASSERTIONS示意代码，不是官方 judge 源码

同一组规则要在每个隐藏 scenario 和 seed 上保持成立

for scenario in hidden_scenarios:
  for seed in scenario.seeds:
    var run = launch_fixed_timestep(
      scenario, seed)

    while not run.finished:
      run.advance_one_tick()
      assert(resources_are_conserved(run))
      assert(event_order_is_legal(run))
      assert(no_collision_violation(run))

    assert(run.completed_required_goal())
Scenario作者手工定义测试结构，例如接近方向、地图与输入计划。
Seed给场景的数值参数取值；scenario × seed 是一个 case。
Tick在错误刚发生时失败，不让后续状态掩盖它。
按 §3.1 写的不可运行协议伪代码，不是每题官方 checker；未取得具体隐藏断言和容差。

到终点还不够：整条轨迹不能碰墙

decide(state)

16 · CASE / COMBOPlatform Guard

名单包含所有真实坐标；控制器仍必须判断目标是否可见

Platform Guard

每帧返回 move、jump、chasing；intruders 是完整坐标名单，不能直接当作可见目标。

巡逻安静期覆盖 home platform 至少 34%。
可见性距离够近且视线无阻挡；不能追墙后的目标。
地面接近着地接近至 130 世界单位，空中掠过不算。
返回安静后离家不超过 6 秒，再恢复巡逻。
FAIL 推演：塔后访客仍在名单里，直接返回 chasing=id 却不可见，构成 ghost chase（声称追不可见目标）。隐藏 checker 未取得。
Appendix F.3：watch 1,800 帧 = 30 秒、60 Hz；34%、130 世界单位、6 秒均为公开要求。FAIL 为规则示意，非实测日志。
